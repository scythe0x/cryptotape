# проверка market data → импульс

дата: 20 октября 2026. проверен текущий рабочий checkout, включая незакоммиченные изменения прокси. рабочую логику при проверке не менял.

## вывод

детектор оставлять: монотонные очереди экстремумов дают амортизированное o(1) на окно, каждый ценовой тик проверяется сразу. бакеты 100 мс ограничивают детализацию хранения, а не частоту сигналов. переписывать проект или менять стек для производительности сейчас не требуется.

приоритет — корректность времени, независимость приёма данных от диска и интерфейса, контроль возраста данных и устойчивость служебных соединений. json можно ускорить небольшим изменением после этих исправлений.

## текущий путь

1. последовательно выполняются rest time → exchangeinfo → ticker/24hr.
2. рынки делятся по 200 всех известных тикеров. подписка bookticker создаётся только для прошедших минимальный оборот.
3. сначала подключается mini-ticker websocket, затем ценовые соединения.
4. кадр websocket → два json.unmarshal → bid/ask → проверка оборота и возраста → engine.process.
5. при пересечении: sqlite insert → синхронный обработчик события, включая показ overlay → отдельные goroutine звука и терминалов.

ценовые тики не имеют отдельной прикладной очереди. при блокировке callback они накапливаются в нижележащих сетевых буферах. канал updates ёмкостью 1 содержит только сигнал пересчитать подписки; объединение этих сигналов само по себе не теряет котировки.

## измерения

среда: apple m3 pro, darwin/arm64, go 1.26.1. два живых прогона по 30 секунд, напрямую, без пользовательского прокси. это тестовый backend без webview, звука и реального терминала. нагрузка в эти минуты не моделирует полный рыночный обвал.

| текущий rest-срез | 748 торгуемых usdt-контрактов, 62 с оборотом ≥ $80 млн |
| подписки | 4 ценовых соединения: 15 / 14 / 20 / 13 тикеров; ещё одно для mini-ticker |

возраст события оценён по e и поправке часов через rest midpoint. это не точный односторонний сетевой пинг и не время появления карточки. во втором прогоне задержка превысила цель 2 с при низкой загрузке backend. место задержки до callback отдельно не локализовано: возможны upstream, маршрут и буферизация при чтении. один websocket rtt не подтверждает свежесть котировок.

pprof второго прогона: существенная доля cpu приходится на системное чтение tls/websocket и работу runtime; engine.process — около 0,9% cpu samples cumulative. json важен для выделений памяти, но сокращение времени его микробенчмарка на 34% не означает ускорение всего приложения на 34%. из примерно 160 мб суммарных выделений за прогон около 50 мб flat приходится на io.readall, 26 мб — на json.unmarshal, 20 мб — на context.afterfunc. это оборот выделений, не удерживаемая память.

## исправления по приоритету

### 1. считать окно по времени события

`internal/core/engine.go:158–172`: окно индексируется received вместо eventtime. воспроизведены оба эффекта для правила 10% / 5с:

- первое событие пришло на 7 с позже, второе свежее: падение 11% за 7 с ошибочно считается движением за 5 с;
- второе событие пришло на 6 с позже: настоящее падение 11% за 1 с пропускается, поскольку локальное время между получениями превышает окно.

нужно разделить часы: время события — для истории и окна, время получения/монотонное время — для ожиданий и возраста соединения. дополнительно определить политику неупорядоченных/повторных событий. сейчас проверка received.before(last) не проверяет порядок биржевых событий.

### 2. убрать диск и интерфейс из чтения websocket

`internal/desktop/controller.go:191`: insertalert и emit вызываются прямо из callback чтения ценового потока. sqlite использует одно соединение и busy_timeout 3000 мс. искусственный write lock на 200 мс заблокировал callback и алерт на 236 мс.

нужен отдельный обработчик сохранения и действий с ограниченной очередью кандидатов. сам детектор можно оставить в обработке каждого тика. запись должна по-прежнему предшествовать публикации алерта. переполнение очереди — явная ошибка; размер, возраст старейшего элемента и задержку записи измерять. объединять записи в короткие транзакции можно без искусственного ожидания накопления пачки.

`main.go:112`: первый showoverlay дополнительно вызывает getsnapshot и читает 100 записей истории. для позиционирования достаточно уже известных настроек монитора. показ окна также стоит отделить от отправки терминальной команды.

### 3. контролировать возраст данных отдельно от ping

`internal/binance/feed.go:342`: отбраковка происходит только после 10 с. диапазон 2–10 с остаётся пригодным для сигналов и не обязательно отражается в статусе как деградация. живой прогон показал, что этот диапазон достижим при текущем маршруте.

нужны метрики по каждому соединению: возраст события до декодирования/детектора, время обнаружения, сохранения, отправки команды и фактического отображения карточки. превышение цели 2 с обозначать деградацией, свыше 10 с запрещать действия. p99 до карточки на windows пока не измерен.

### 4. разделить цену и служебные обновления

`internal/binance/feed.go:351`: отказ mini-ticker отключает обработку всех цен и сбрасывает всю историю. `feed.go:173`: единичная ошибка rest refresh отменяет весь feed, даже если ценовые websocket исправны.

служебные запросы должны восстанавливаться независимо. последний проверенный срез оборота можно использовать только с явной политикой допустимого возраста. здесь есть выбор: сохранить realtime mini-ticker или перейти на уже запрошенную пользователем проверку оборотов раз в 5 минут. второй вариант проще и исключает лишнюю обязательную зависимость. новые листинги всё равно обнаруживаются через exchangeinfo.

### 5. ускорить json без смены библиотеки

`internal/binance/feed.go:313`: combined frame разбирается дважды, rawmessage копирует data. один unmarshal в структуру с вложенным booktick в локальном сравнении дал −34% времени декодирования и −45% выделяемых байтов. это первый разумный шаг оптимизации cpu/gc.

важно сохранить отдельные поля b/B и a/A: стандартный json декодер допускает сопоставление без учёта регистра, поэтому простое удаление полей количества может вернуть старую ошибку подмены цены количеством. подходящий регрессионный тест уже есть.

### 6. гарантировать управление подписками

`internal/binance/feed.go:316`: ответы без data пропускаются, включая подтверждения и ошибки subscribe/unsubscribe. счётчик соединений увеличивается до подтверждения подписки. успешный websocket handshake ещё не доказывает, что нужные тикеры слушаются.

нужны контроль id/ack/error и таймаут подтверждения; ограничение управляющих сообщений на соединение; проверка числа потоков при добавлении листингов. в обычной работе текущие пакетные запросы не отправляют отдельное сообщение на каждую монету, поэтому сам массовый пролив не должен создавать сотни subscribe в секунду.

### 7. проверить предел терминала при серии

`internal/desktop/terminal.go:28`: vataga ограничена 32 одновременными http-соединениями и общим таймаутом клиента 1,5 с. при 750 одновременных вызовах к тестовому терминалу с ответом через 100 мс успешно завершились 448, 302 завершились ошибкой; к моменту завершения клиентов сервер получил 485 запросов.

это не измерение скорости настоящей vataga. тест доказывает, что «каждый алерт породил goroutine» не гарантирует отправку каждой команды: часть может исчерпать таймаут в очереди http transport. нужна явная очередь команд с измерением возраста и отдельными стадиями ожидания/отправки/ответа, без объединения или отбрасывания разных тикеров. допустимую конкурентность подтвердить на реальном терминале.

## rate limits

- rest-цикл: time весит 1, exchangeinfo — 1, все ticker/24hr — 40: суммарно 42 на запуск и каждые 5 минут, в среднем 8,4 weight/мин. текущий exchangeinfo вернул лимит 2400 weight/мин; обычная нагрузка скринера — около 0,35% этого лимита. общий ip прокси может использоваться другими приложениями.
- rest get не анализирует used-weight и специальную обработку 429/418. при ограничении не следует повторять запросы только по обычному расписанию 1/2/4/8 с: нужно учитывать информацию биржи о лимите и сроке блокировки, включая retry-after, если он присутствует.
- websocket: до 1024 потоков на соединение, до 10 входящих для биржи управляющих сообщений/с. это не ограничение количества получаемых рыночных тиков. текущие 200 потоков на shard имеют запас, но общий limiter отсутствует.
- соединение живёт до 24 часов. сейчас ожидается разрыв и выполняется reconnect со сбросом истории. для непрерывной работы полезна плановая смена соединения с коротким перекрытием и дедупликацией, без пропуска и двойной обработки тиков.

## что пока не стоит усложнять

- переписывать экстремумы на другую структуру: текущая стоимость мала; дублирующее обновление общего окна у нескольких правил можно убрать позднее.
- уменьшать число ценовых соединений только ради числа сокетов: четыре соединения также распределяют чтение и декодирование, а их текущая цена мала.
- переходить на all-market bookticker: его заявленная частота 5 с не подходит для короткого ножа; отдельные bookticker realtime выбраны правильно.
- заменять bookticker на aggtrade только ради экономии: поменяется наблюдаемая цена и семантика сигнала. такой вариант требует отдельного сравнения на одних и тех же движениях.

## воспроизведение замеров

диагностические тесты и pprof сохранены локально в `build/bin/market-audit/`; они не входят в приложение. go overlay подключает их к пакетам, не меняя рабочие исходники:

```sh
go test -overlay build/bin/market-audit/overlay.json ./internal/core ./internal/desktop -run '^TestAudit' -v
go test -overlay build/bin/market-audit/overlay.json ./internal/core ./internal/binance -run '^$' -bench BenchmarkAudit -benchmem
go tool pprof build/bin/market-audit/live.test build/bin/market-audit/live.cpu.pprof
```

overlay содержит абсолютные пути текущего checkout. живой тест не входит в обычный набор; запускать его следует отдельно и осознанно. обычные тесты core/binance/storage/desktop прошли. существующий crash-тест также сохранил все 1500 сигналов; его sqlite insert p99 составил 154 мкс.
